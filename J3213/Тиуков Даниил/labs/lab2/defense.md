## Кратко о проекте

TripPlanner — учебное travel-приложение для планирования поездок: каталог направлений с фильтрами, личный кабинет с маршрутами/заметками/избранным и раздел совместного планирования.

Стек: HTML5, CSS3, Bootstrap 5, Vanilla JavaScript. Бэкенд — `json-server` (REST). Многостраничный сайт (7 HTML-страниц), без сборщика.

В ЛР1 всё хранилось в `localStorage`. В ЛР2 добавил настоящий REST-бэкенд и переписал всю работу с данными.

---

## 1. json-server как имитация бэкенда

Подключил `json-server` зависимостью и добавил скрипт `npm run server`, который поднимает `http://localhost:3000`.

Создал `db.json` с **10 REST-коллекциями**: `users`, `destinations`, `reviews`, `routes`, `notes`, `favorites`, `participants`, `stages`, `shared-notes`, `ideas`.

**Зачем:** заменить браузерный `localStorage` настоящим HTTP-API — теперь данные живут на сервере, доступны всем страницам и переживают чистку браузера.

---

## 2. Слой API — модуль `js/api.js`

Сделал отдельный объект `TravelApi` — обёртка над `fetch` с базовыми методами `get/post/put/patch/delete` и обработкой HTTP-ошибок.

Для каждой сущности — именованный метод: `getDestinations`, `addRoute`, `updateNote`, `deleteFavorite`, `addParticipant`, `addStage`, `updateIdea` и т. д.

**Зачем:** в ЛР1 каждая страница лезла в `localStorage` напрямую, и логика была размазана. В ЛР2 страницы вызывают только методы `TravelApi`, не зная про `fetch` и URL'ы — стандартная клиент-серверная архитектура.

---

## 3. Регистрация и вход через REST

**Регистрация** (`TravelApi.register`): сначала `GET /users?email=…` — проверяю уникальность email; если пользователя нет, делаю `POST /users` с данными формы.

**Вход** (`TravelApi.login`): делаю `GET /users?email=…&password=…` — если массив не пустой, пользователь найден, кладу его в сессию.

В `localStorage` остался только ключ `tripplannerCurrentUser` — текущая сессия. Сами пользователи теперь в `db.json` на сервере.

---

## 4. Перенос всех CRUD на сервер

Все операции, которые в ЛР1 шли через `localStorage`, теперь идут через REST:

| Раздел | ЛР1 | ЛР2 |
|---|---|---|
| Каталог направлений | хардкод | `GET /destinations` |
| Отзывы | localStorage | `GET/POST /reviews?destinationId=` |
| Маршруты | localStorage | `GET/POST/PATCH/DELETE /routes` |
| Заметки | localStorage | `GET/POST/PATCH/DELETE /notes` |
| Избранное | localStorage | `GET/POST/DELETE /favorites` |
| Участники | localStorage | `GET/POST /participants` |
| Этапы | localStorage | `GET/POST/PATCH/DELETE /stages` |
| Общие заметки | localStorage | `GET/POST/DELETE /shared-notes` |
| Идеи и голоса | localStorage | `GET/POST/PATCH /ideas` |

**Зачем:** добавление/изменение/удаление везде идёт через привычные HTTP-глаголы; код страниц стал чище.

## 5. Защищённые разделы (auth guards)

`dashboard.html` и `collaboration.html` теперь требуют авторизации: если в сессии нет пользователя — редирект на `login.html`.

В навбаре пункты «Кабинет» и «Совместное планирование» помечены `data-auth-only` — показываются только залогиненным. Пункты «Вход»/«Регистрация» — `data-guest-only`, только для гостей. Переключение делает `TravelApp.syncAuthNavigation`.

В кабинете добавил кнопку **выхода** — чистит сессию и возвращает на главную.

---

## 6. Светлая и тёмная темы

Переключатель в navbar (иконка солнце/луна). Выбор пишется в `localStorage` под ключом `tripplannerTheme`.

В `<head>` каждой страницы стоит **inline-скрипт**, который применяет тему **до отрисовки контента** — чтобы при загрузке тёмной темы не мигало белым.

При первом заходе учитываю системную настройку `prefers-color-scheme`. Если пользователь руками тему ещё не выбирал, отслеживаю смену системной — сайт подстраивается.

## 7. Toast-уведомления

Сделал общий метод `TravelApp.showToast(message, type)` — создаёт Bootstrap-toast в контейнере `#toastContainer`. Использую везде в формах: «Маршрут добавлен», «Идея добавлена», «Ошибка при сохранении» и т. д.

**Зачем:** в ЛР1 были инлайн-алерты прямо в формах — выглядело шумно. Toast корректнее и единообразнее.

## 10. Как запустить

```bash
cd travel-planner
npm install
npm run server   # http://localhost:3000 — json-server
```

HTML открывать через статический сервер (например, `npx serve .` или из WebStorm), **не** как `file://` — иначе CORS заблокирует запросы к `localhost:3000`.

## Возможные вопросы на защите

**— Почему `json-server`, а не настоящий бэкенд?**
Лабораторная про фронтенд. `json-server` даёт REST-семантику (GET/POST/PATCH/DELETE, фильтры по query-параметрам) без написания собственного сервера — этого достаточно, чтобы отработать клиентскую часть по-настоящему.

**— Пароли в `db.json` хранятся в открытом виде — это нормально?**
Это учебный мок. В реальной системе на сервере был бы хеш (bcrypt/argon2), регистрация и логин шли бы через выделенные эндпоинты, а не через прямой `GET /users?password=`. Здесь `json-server` фильтрует по полю — это компромисс ради простоты.

**— Что в сессии хранится?**
Только объект пользователя (id, имя, email) в `localStorage` под ключом `tripplannerCurrentUser`. Никакого токена — `json-server` авторизацию не делает.

**— Как работает проверка уникальности email при регистрации?**
Сначала `GET /users?email=<введённый>`. Если массив пустой — email свободен, делаю `POST /users`. Если не пустой — показываю ошибку, `POST` не делаю.

**— Почему inline-скрипт для темы в `<head>`?**
Если применять тему после загрузки CSS и JS, при тёмной теме сначала мелькает белый фон, потом перекрашивается — мигание. Inline-скрипт в `<head>` ставит `data-theme` до того, как браузер отрисовал body, — переход незаметен.

**— Какие методы HTTP используются и где?**
`GET` — чтение коллекций и фильтрация. `POST` — создание (новый маршрут, заметка, идея, пользователь). `PATCH` — частичное обновление (редактирование заметки, голосование за идею). `DELETE` — удаление (убрать из избранного, удалить маршрут). `PUT` я не использовал, так как везде хватает `PATCH`.
